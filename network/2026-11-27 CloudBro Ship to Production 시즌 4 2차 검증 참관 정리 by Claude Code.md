## 요약

2026년 11월 27일(금) 오후 8:05 시애틀 시각(한국 11월 28일 토요일 오후 1:05)부터 약 2시간 동안, **CloudBro**의 오픈소스 인큐베이팅 프로그램 **Ship to Production(STP) 시즌 4 · 2차 검증**이 Google Meet 온라인으로 열렸다. Builders Lounge 운영자 **박창수**와 멤버 **김성진(James)**이 「**시애틀 기술검증단**」으로 처음 참여했다. 오프닝에서 두 사람이 Builders Lounge를 소개했고, 이어서 네 프로젝트 팀(**CUBRID Lab · T2 · 두레 · ARG**)이 각각 발표 10분 + Q&A 10분으로 2차 검증 발표를 했다. 다섯 번째 팀(엑토리)은 사정상 최종 발표 때 오프라인으로 발표하기로 했다. 질의응답에서는 기술검증단이 쿠버네티스 Operator 설계, 장애 탐지 카탈로그, 조직 지식 엔진의 티어 구조, LLM 평가 프레임워크 같은 실무 조언을 줬다. 마지막에 박창수 · 김성진이 소감을 말했고, CloudBro는 12월 11일 「**CloudBro Ship Night**」 행사와 1월 중순 최종 발표 일정을 안내했다.

> 영상은 공개하지 않는다(CloudBro 프로그램 내부 검증 세션 녹화). 이 문서는 Builders Lounge 운영진이 참관한 내용을 정리한 것이다.

## 발표 1 — CUBRID Lab 「CUBRID K8s Operator」

- **팀**: CUBRID Lab (Yeongseon Choe · Gyeongjun Paik · 공동 메인테이너). 발표는 Gyeongjun Paik.
- **한 줄 소개**: 「DB 서버가 장애로 바뀌었습니다. 앱은 언제 다시 써도 될까요?」 — 오픈소스 DB **CUBRID**를 쿠버네티스에서 운영하기 위한 **Operator + Instance Manager**.
- **구조**: Operator가 Kubernetes API로 DB 상태를 감시하고 쓰기 차단 · 승격 · 백업 결과 기록을 맡고, Instance Manager가 DB 인스턴스와 1:1로 붙어 상태 확인 · 백업 · 복원을 돕는다. CUBRID HA는 복제를, Broker는 애플리케이션 요청을 DB SQL로 전달한다. 백업은 S3 호환 저장소.
- **1차 피드백 반영**: 「상태 이상 표시만으로는 쓰기를 막을 수 없다」는 피드백에 따라, 이상이 있으면 쓰기 연결을 끊고 성공 응답이 없는지 확인하고 쓰기용 Broker를 대상에서 제외하도록 했다.
- **검증 시나리오**: 설치 · 기동 확인, 서버 강제 종료(graceful shutdown 0초) 후 「성공 응답을 받은 쓰기가 실제 DB에 남았는지」 대조, master 인스턴스 연속 장애, 백업으로 새 클러스터 복원, 디스크 삭제 복구 등. 쓰기 중단 시간 · 불필요한 차단 · 누락 데이터를 측정.
- **결과**: 차단 뒤 쓰기 성공 0건 테스트는 대부분 통과, 새 클러스터 복원 3회 통과. 카오스 실험 중 **공식 CUBRID Operator가 두 번째 장애 때 DB를 다시 띄우지 못하는 버그**를 우연히 발견했고, 이 팀의 Operator는 약 30초 뒤 다시 떠서 쓰기까지 복원됐다(첫 복구는 공식 Operator가 더 빨랐음).
- **남은 문제**: 차단 순간에 쓰인 데이터 일부 누락 · 장애 노드에 쓰인 데이터가 새 DB와 싱크되지 않는 멱등성 문제 → v0.2. 복제 지연 단축, CSI 외부 볼륨 연동, 공식 Operator 측과의 협의는 아직.
- **v0.1 공개 기준**: 필수 안전 시험(차단 뒤 쓰기 성공 0건, 복구 시간 측정)을 모두 통과하면 v0.1 공개. 12월에 공개 후보 확정과 장애 시험 반복, 다른 운영자가 문서만 보고 설치 · 복구 · 백업 복원을 재현하는지 검토.
- **팀이 던진 질문**: ① 복제는 정상처럼 보이는데 서버 한 대만 안 된다면, 무엇을 확인하고 쓰기를 다시 열 수 있다고 믿을까? ② 백업으로 복원한 뒤 운영자가 성공이라고 판단하려면 어떤 결과를 확인해야 할까?
- **Q&A**: 기술검증단 Je Min Kim이 DB Operator를 만들 때 StatefulSet · PV/PVC에서 어려움이 많다며 도움을 제안하고, StatefulSet(Pod 이름 고정 · 순서 · 고정 PV 매핑)과 Deployment(상태 없음 · 자유로운 스케일)의 차이를 정정해 줬다. 보통 Broker를 쓰는 데는 이유가 있으니 Broker 쪽 설계도 고민해 보라고 했다. 팀은 공식 Operator와 달리 read/write Pod를 분리하면서 동기화 문제가 생겼다고 설명했고, 「AI 에이전트 도움을 많이 받아 시나리오만 통과하면 될 줄 알았는데 시행착오가 많고, 제공 서버를 무한정 돌릴 수 없어 실험이 지연된다」고 털어놨다. 질문을 정리해 따로 통화하기로 했다.

## 발표 2 — T2 「인프라 장애 Known Issue 진단 도구」

- **한 줄 소개**: 서버 오류 로그를 미리 알려진 문제(Known Issue) 목록과 대조해 원인과 조치 방법을 알려 주는 도구. MLOps · DevOps 엔지니어들로 구성된 팀이 실제 운영의 불편을 줄이려고 기획했다.
- **1차 피드백 반영**: 판정은 규칙으로만 하고 LLM은 리포트에만 쓰도록 분리. 로그 원문과 「못 모은 정보와 그 이유」를 함께 표시. 평가 사례 8건(GitHub 이슈 등 외부 4 + 합성 4). 데이터 형식은 **OpenTelemetry**, 보안 취약점은 **OSV** 형식 채용. 서버명 · IP 등 민감 정보 자동 마스킹. GPU는 가상 GPU(NVIDIA mock)로 구현.
- **데이터 팩**: 공식 문서를 파싱해 원문 대조(verify)를 통과한 것만 수록. NVIDIA GPU 853건, 리눅스 · 쿠버네티스 약 100건 등 약 1,000건. 변경 시 CI 19단계로 검사.
- **구성**: Zadara Cloud VM 2대 — T2 서버(수집 · 마스킹 · 대조 · 판정 · 화면)와 쿠버네티스 테스트 서버. node-exporter와 Vector는 K8s가 깨져도 데이터를 볼 수 있게 호스트에 직접 데몬으로 둠. 대시보드(호스트 · 수집 상태 · 버전 검토 · 설정 · 감지 레코드, 판정 none · possible · known). 조치는 아직 운영자가 수동으로.
- **고민 세 가지**: ① Stack Overflow 같은 커뮤니티 글은 형식이 제각각이라 크롤링 자동화가 어려움 — 레코드 늘리기를 사람 손에서 떼는 법 ② 팩 갱신을 GitHub PR까지는 자동화했지만 운영 서버까지 반영하는 법 ③ 다른 회사 소프트웨어에 라이브러리처럼 붙이는 방법.
- **12월 계획**: 오픈소스 공개 — 판정 엔진, LLM 리포트 보강, 외부 평가 사례 15건, 문서만 보고 설치 가능하게.
- **Q&A**: 기술검증단(CloudBro 커뮤니티 다른 오픈소스 프로젝트 메인테이너)이 비슷한 고민(호환성 매트릭스 · 보안 취약점 업데이트 자동화)을 공유하며, 취약점 정리와 팩 생성을 Gemma 4 같은 작은 로컬 모델 에이전트로 시간을 들여 자율 순환시키는 구조를 제안했다. Je Min Kim은 ① 에러를 한 건씩 판정하면 정확도가 떨어지니 **시간 윈도우**로 묶어 볼 것 ② 에러 상황별로 체크 규칙 · 볼 로그 · 볼 메트릭을 정리한 **서비스 카탈로그**를 프레임워크화할 것 ③ 외부 제공은 **OpenTelemetry**(Prometheus 메트릭 등 포함) 기반으로 할 것을 제안했다.

## 발표 3 — 두레 「검증된 기억만 지식으로 승격하는 메모리 엔진」

- **한 줄 소개**: AI 에이전트가 쓰는 공유 메모리에서 모든 기록은 기억(Memory)으로 저장하고, 테스트 · 리뷰 · 사람 판정 같은 **확인 신호**가 있는 것만 지식(Knowledge)으로 승격, 실패가 확인되면 강등.
- **1차 피드백 반영**: 에이전트의 자기 보고는 근거에서 제외, 「전부 승격」 기준선과 비교, 시드 12개로 편차 확인, 외부 벤치마크(LoCoMo) 도입, 실제 에이전트 데모에서 테스트 실패 시 강등 확인, 같은 범위 소유자 안에서만 노출.
- **구조**: 코어 런타임(기록 보관 · 인덱싱 · 권한 확인 · 결정 검증), v0.1은 PostgreSQL + pgvector, 교체 가능한 엔진(팀원 3명이 각자 엔진 후보를 만들어 비교), 별도 평가 하네스.
- **알게 된 것**: ① 효과는 엔진별 승격 아이디어가 아니라 공통 「**실패하면 강등**」 규칙에서 나왔다 — 틀린 기억을 따르는 비율이 기준선 81.8%에서 18~23%로 감소. ② 확인 신호가 없는 일상 대화(LoCoMo 152문항)에서는 단순 검색과 같았다 — 일반 대화 기억은 Mem0 · Hindsight 같은 기존 도구가 이미 더 잘한다. ③ 임베딩 유사도로는 같은 말인지 반대말인지 구분 못 함 → 판정에 LLM을 넣자는 판단.
- **노선 변경**: 코딩 도구에는 이미 메모리가 있고 코드에서 드러나는 지식은 모델이 이미 안다. 그래서 대상을 개인 코딩에서 **확인 신호가 업무 안에 있는 팀과 기업**(코드 리뷰 · CI 승인 등)의 오래 지켜야 할 결정과 정책으로 옮겼다.
- **검증단에 던진 질문**: ① 팀 · 기업 지식으로 대상을 옮기는 게 맞나, 기업이라면 어떤 지식부터 쓰고 싶나? ② 최신 모델은 규칙을 정해 주면 오히려 나빠지고 이전 모델은 명시적 지시로 좋아졌다는 보고(Claude 공식 아티클 — Sonnet 4.6 이후 메모리를 자세히 지시하면 오히려 성능 저하)가 있는데, 어떤 모델을 주 타깃으로? ③ 판정에 LLM을 넣는 게 맞나(토큰 비용 · 디버깅 어려움), 작은 모델로 충분한가?
- **Q&A (Je Min Kim, 비슷한 시스템을 만들고 있다며 답변)**: ① 팀 · 기업으로 옮기는 게 맞다. 단순 코딩용 메모리는 메리트가 적고, 큰 조직은 함께 만든 지식을 한곳에 두고 나눠 써서 토큰도 준다. ② 모델이 좋아질수록 strict한 주입은 의미가 줄어드니 **어떤 모델을 쓰든 상관없게** 만들 것. ③ 질문을 **티어**로 나눈다 — 티어 1: LLM 판정 없이 키워드 · 룰로 바로 답, 티어 2: 임베딩 검색으로 답, 티어 3: LLM이 정형 · 비정형 데이터와 온톨로지 · 그래프까지 써서 복합 질문에 답. 또 지식의 **가드(guard)** 역할을 사람에게 두고, 파이프라인이 LLM으로 지식을 분류해 오브젝트 스토리지 · 벡터 DB · 그래프 DB에 넣고 확신도(예: 80%)를 매기면, 80% 이하 애매한 것만 가드가 검토 · 승인해 버전을 올리고, 실제 사용자의 피드백이 다음 파이프라인에 반영되는 루프를 운영한다. 사용자 부담에 대해서는 「지금 쓰는 사람들에게 이미 업무 프레임워크가 되고 있어 거부감이 크지 않다」고 답했다. 박창수는 관련 영상을 채팅으로 공유했다.

## 발표 4 — ARG 「Agent Reliability Gate」

- **팀**: Team T1 (김동석 · Lee Eun Chong). 발표는 Lee Eun Chong.
- **한 줄 소개**: 「변경이 품질을 깎지 않게, 릴리스 전에 막습니다」 — 모델 · 프롬프트 · 에이전트 코드를 바꾸는 PR이 올라오면 바꾸기 전(base)과 후(head)를 같은 입력으로 돌려 비교하고, PR에서 통과 · 차단을 정하는 **오픈소스 릴리스 게이트**.
- **판정 4단계**: fail(기준을 넘는 회귀 · 비교 불가) · not_ready(필요한 승인 부족) · warn(주의하되 차단 안 함) · pass. 원칙은 「모르면 통과시키지 않는다」 — 정답률 · 안정성 등은 fail 규칙, 나머지 6개 지표는 warn 규칙.
- **1차 피드백 반영 (8개 중 6개 대응, 2개 일부)**: 실제 데이터(공개 CI 로그) 사용, 다른 계열 모델 교차 채점, 반복 흔들림 · 임계값 · A/A 측정, 적용 지점(CI)과 경계 명확화, 토큰 측정 · 예외 승인 · 감사 기록. 라이선스를 확인한 데이터만 저장소에 두고 나머지는 테스트 후 폐기.
- **미룬 것**: 팀 · 키별 토큰 한도 차단(LiteLLM이 이미 제공), 공개 벤치마크 절대 점수(업무 회귀에 답하지 못함), 단일 종합 점수(모델마다 편향이 달라 일치율 기준으로), 판정 모델 버전 고정(기록만), 협력 팀 실사용(아직 0곳).
- **구조**: PR 평가는 GitHub Actions + Zadara 러너에서 `arg run`으로 base/head 실행, 교차 판정은 Upstage Solar Mini 4. 웹 실행은 쿠버네티스 평가 Job + LiteLLM, 메인 판정 Solar Pro 4, 교차 판정 gpt-6-luna(다른 제공사). ARG 서버(API + PostgreSQL)가 승인 · 감사 · 정책을 결정하고 웹 콘솔(대시보드 · 비교 · 승인 · 사용량)로 확인. 판정 · 승인 · 감사는 직접 만들고 LiteLLM · DeepEval · Langfuse · Trivy · PostgreSQL은 연결해서 쓴다. 응답 원문은 서버에 저장하지 않고 점수만 집계.
- **측정 결과**: 판정 모델 간 일치도 κ(카파) — 합성 데이터 0.78 vs 실제 0.44. 판정 모델 일치율 합성 95.8% vs 실제 79.8%. 프롬프트에서 라벨 두 개를 지운 PR은 정답률 -15.3%p로 실제 차단. 정답률 허용 하락 약 3%p를 넘으면 회귀가 유의미. 미리 적은 기대와 PR 5건(#277~#281) 판정이 모두 일치. PR 1회 평가 약 4분 · 약 $0.045(약 217k 토큰, 판정 호출이 비용의 70%). 질문 트리 방식은 한 번 호출보다 성능이 낮아 CI 분류에서 제외.
- **검증단에 던진 질문**: ① 결과물의 핵심이 코드가 아니라 실데이터로 다듬은 분류 프롬프트인데, 오픈소스로 프롬프트까지 공개해야 하나? ② 판정 모델끼리 약 20%가 갈리는데, 사람이 확인하는 방식과 판정 모델을 더 붙여 자동으로 정하는 방식 중 무엇이 나을까?
- **최종 발표까지**: v0.2를 라이선스가 허용하는 범위에서 공개(ARG 코드 공개, LogChunks CC BY 4.0 표기, 라이선스 불명 데이터 비공개), 다른 제공사 교차 판정, 협력 팀 실제 로그 확보, 잠정 라벨 확정, GitHub App 설치 후 저장소 공개.
- **Q&A (Je Min Kim)**: 프롬프트만 공개하기보다 평가 **프레임워크**로 제공하라 — 오프라인 · 온라인 · 데이터 기반 · LLM 기반 · 룰셋 평가를 고를 수 있는 템플릿 구조. LLM이 모든 걸 해결하지 않으니 룰 베이스도 함께 제공하고, 지표도 품질만이 아니라 작업 순서, **가드레일(개인정보 포함 여부)**, 비용 같은 기업이 중시하는 항목을 기본으로 넣고 사용자가 커스터마이징하게 하라.
