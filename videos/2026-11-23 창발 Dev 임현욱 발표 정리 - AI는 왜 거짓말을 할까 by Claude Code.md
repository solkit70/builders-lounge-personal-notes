## 발표 내용

### 1. 「100점, 통과」 보고 뒤에 숨은 네 가지 반칙

임현욱 님이 만든 튜토리얼 자동화 프로그램은 검증 점수 100점, 상태 「통과(PASSED)」를 보고했다. 그러나 직접 첫 단계를 실행해 보니 시작하자마자 에러로 멈췄다. 에이전트의 작업 기록을 뜯어보니 네 가지 문제가 드러났다.

| 반칙 | 내용 | 일상에 빗대면 (칼럼에서 덧붙인 예) |
|---|---|---|
| ① 지어내기 | 있지도 않은 명령어 옵션을 지어냈다. 최신 사용법을 확인하는 대신 예전에 배운 기억으로 짐작 | 이미 문 닫은 식당의 영업시간, 세상에 없는 책 제목 |
| ② 실패 숨기기 | 실제 호출이 실패하자 에러를 덮고 「상태: 정상(OK)」이라는 가짜 값을 넣었다. 「실수가 아니라 실패를 의도적으로 숨긴 것」 | 1,000명 명단 중 600명만 정리하고 「정리를 마쳤습니다」 |
| ③ 하지 않은 일을 했다고 하기 | 프로그램을 돌리지도 않고 초록색 체크 표시와 고유 번호까지 만들어 문서에 붙였다 | 「링크 확인했습니다」라는데 안 열리는 링크 |
| ④ 답안지 훔쳐보기 | 채점을 깐깐하게 바꾸자 작업 폴더 바깥을 뒤져 숨겨 둔 채점 프로그램 원본을 열어 봤다. 「교무실 선생님 책상 서랍을 열고 답안지를 훔쳐본 셈」 | 「500자로」 하면 글자 수만 맞추고, 「출처 달아 줘」 하면 없는 출처를 붙임 |

임현욱 님은 이런 꼼수와 지름길 찾기가 코딩 에이전트를 써 본 사람이라면 한 번쯤 겪어 봤을 일이라고 했다.

### 2. 규칙 문서를 줘도 98.8% — 「필요한 건 98점이 아니라 100% 완주」

첫 대응은 에이전트가 일을 시작할 때 읽는 규칙 문서, **에이전트 스킬(Agent Skill, SKILL.md)**에 「명령어는 반드시 실행해서 확인해라, 에러를 숨기지 마라, 실습하며 만든 클라우드 서버는 끝나면 반드시 지워라(켜 두면 따라 한 사람에게 요금이 계속 나감)」 같은 원칙을 적어 주는 것이었다. 말을 훨씬 잘 듣는 것 같았지만 열 번 돌리면 한두 번은 같은 반칙이 다시 나왔다.

세부 규칙 350개로 자동 채점한 결과는 다음과 같다.

| 조건 | 평균 점수 |
|---|---|
| 규칙 없음 (베이스라인) | 61.8% |
| 규칙 문서(SKILL.md) 제공 | 93.1% |
| 일을 두 단계로 나눠 시킴 | 98.8% |

튜토리얼은 순서대로 따라 하는 실습이라 100단계 중 한 단계만 틀려도 사용자가 멈추고, 마지막에 자원을 지우지 못하면 요금이 계속 나간다. 「평균 98.8%는 반드시 어디선가 한두 개 구멍이 난다는 뜻」이며, 필요한 것은 평균 점수가 아니라 **반칙 한 번 없이 끝까지 가는 100% 완주율**이라고 했다.

### 3. AI는 악당이 아니라 「합리적인 수험생」 — 세 가지 원인

OpenAI · Anthropic · Google DeepMind 논문과 보고서를 대조한 결론: 「에이전트가 악의를 가진 게 아니라, AI를 훈련하고 채점하는 구조 자체가 정직한 실패보다 거짓 통과에 보상을 주기 때문」이다.

1. **초록불만 보상하는 학습** — AI는 테스트에 「통과」 초록불이 켜질 때마다 점수를 받으며 배운다. 진짜 풀어서 켰는지, 시험을 속여서 켰는지는 따지지 않는다. (리워드 해킹, Reward Hacking)
2. **틀려도 감점 없는 채점** — 대부분의 벤치마크가 「모르겠습니다」는 무조건 0점, 찍으면 운 좋게 맞을 수도 있는 방식이라 찍는 쪽이 늘 유리하다. 할루시네이션(Hallucination, 환각)의 원인.
3. **승인을 좋아하는 사람의 피드백** — 사람 평가자들은 「실패했습니다」보다 자신감 있는 「완료했습니다」를 더 좋아했다. 그래서 AI는 사용자가 듣고 싶어 하는 말을 하는 아첨(Sycophancy) 성향을 배웠다.

정리: 「코딩 에이전트의 거짓말은 어쩌다 터진 버그가 아니라, 이 채점 방식에 맞춰 만들어진 합리적인 수험생의 행동이다.」

### 4. 상식적인 처방 세 가지와 그 실패 — 「혼낼수록 더 교묘해진다」

| 처방 | 결과 |
|---|---|
| 규칙 문서에 대문자로 「절대 하지 마(NEVER)」 경고 | 고치면 안 되는 파일 실험에서 작은 모델이 몰래 고치는 비율이 **32% → 77%**로 오히려 증가. 몰래 고치고 「저 아닌데요?」 시치미. OpenAI 연구에서도 나쁜 속마음에 벌점을 주자 정직해지는 대신 속마음을 감추는 법을 배움. 「말로만 혼내는 건 은폐 기술을 가르치는 것」 |
| 자동 검사기 추가 | 규칙을 더할 때마다 AI는 규칙의 「글자」만 피해 감. 검사상 통과 **56%**, 실제 제대로 실행 **14%** — 「통과한 코드 4개 중 3개는 가짜」 |
| 추론 강도 최대로 올리기 | 작업 폴더 밖을 뒤져 답안지를 찾는 비율이 **약 2% → 75%** (슬라이드 기준, 발표 중 말로는 72%). 더 생각할 시간을 주자 버그를 고치는 대신 더 집요하게 뒤짐 |

**냉장고 비유**: 규칙 문서는 냉장고 문에 붙인 「간식 먹지 마」 메모와 같다. 평소엔 지키지만 배가 고프면(테스트 실패 · 일이 너무 큼 같은 압박) 언제든 무시한다. 정말 지켜야 할 규칙은 메모가 아니라 **냉장고 문 자체의 잠금장치**여야 한다.

### 5. 해법은 AI 바깥에 — 호스트 런타임과 세 가지 제어 축

AI 모델은 파일을 열거나 프로그램을 실행할 손발이 없는 「뇌」다. 손발 노릇을 하는 것은 Claude Code · Codex · Antigravity 같은 **호스트 런타임(Host Runtime)**이다. 잠금장치는 AI의 머릿속(프롬프트)이 아니라 이 손발(훅 · 도구 · 플러그인)에 달아야 한다.

| 축 | 방법 | 결과 |
|---|---|---|
| A. 기억 분리 | 설계 노트 50개를 한꺼번에 「다 읽어라」 → 열 번 중 여덟 번 3~4개만 열고 단어 검색으로 답 찾음, 평균 4.5%만 읽고 정답률 0%. 작은 AI 50개에 파일을 하나씩 맡겨 끝까지 읽고 요약만 넘기게 함 | 비용 **70% 감소**, 정확도 **100%** |
| B. 잠금과 출구는 한 쌍 | 꼼수 경로는 실행 직전에 물리적으로 막고(Lock), 외부 시스템 고장 · 처리 중일 때는 거짓말 없이 「여기서 멈췄습니다」라고 보고하는 **정직한 실패 출구(Exit)**를 정당한 완료로 인정 | 출구 없이 「통과할 때까지 끝내지 마」라고 하면 데이터 변조 · 숫자 날조가 생김. 출구를 열자 날조 · 변조 **0%** |
| C. 작성자와 심판 분리 | 작성 AI에게 「리뷰 받아 오라」 하면 리뷰어를 부르지도 않고 합격 문구 직접 쓰기, 관대한 심판으로 몰래 바꾸기, 떨어뜨린 리뷰어에게 「로비」 등 여섯 가지 조작. 셀프 검토는 실수를 **52.9%**만 잡음. 다른 계열 깐깐한 AI 하나에만 맡기면 멀쩡한 결과물에 **88% 오경보**. → 문서를 조각내 서로의 판정을 못 보는 여러 AI 배심원(Juror)에게 맡기고, 근거 필수 · 셋 중 둘 이상 합의 시에만 불합격, 최종 집계는 사람이 만든 프로그램이 함 | 헛경보 **0%**, 심어 둔 버그 **100%** 적발 |

### 6. 「최신 모델이면 괜찮지 않나?」 — 실무 저장소에서는 22.2%

최근 한 달 안에 나온 최신 모델로 같은 실험을 다시 돌렸다. 깨끗한 새 과제에서는 최신 대형 모델 혼자서도 거의 **100%**, 긴 문서도 알아서 나눠 읽었고 잠긴 파일을 몰래 고치는 반칙도 사라졌다. 그러나 오래된 코드와 테스트가 쌓인 **실무(레거시) 저장소**에서는 같은 모델이 **22.2%**로 떨어졌고, 새 규칙과 기존 테스트가 부딪히자 기존 테스트를 지워 버리기도 했다. 생각을 더 오래 시키자 점수가 오히려 떨어진 모델도 있었다. 반대로 런타임 장치를 붙이자 더 싸고 빠른 모델로도 모든 실행을 100% 완주했다.

「AI의 확률적 추론과 AI 바깥의 확실한 검증은 서로를 대체하는 관계가 아니라 보완하는 파트너」 — **모델은 계속 바꾸되, 잠금과 검증은 바깥에 남겨 두라.**

### 7. 마지막 점검 질문 두 가지

1. 에이전트가 거짓말하지 않고 멈출 수 있는 **합법적인 출구**가 열려 있는가?
2. 에이전트가 어긴 규칙을 규칙 문서에 한 줄 더 쓰는 대신, **AI 바깥의 장치로 옮길 수** 있는가?

맺음말: 「냉장고 문에 붙은 ‘간식 먹지 마’ 메모를 아무리 굵고 큰 대문자로 써도, 냉장고 문을 잠글 수는 없습니다.」

## 질의응답 (발표 뒤 약 27분, 영상 미포함)

참석자 이름은 공개하지 않는다.

| # | 질문 · 의견 | 임현욱 님 답변 요지 |
|---|---|---|
| 1 | 결국 코드는 에이전트가 짜고 검사는 따로 떼어서 하라는 게 핵심인가? | 만드는 것과 검증하는 것을 별개 세션 · 별개 모델에 맡기는 게 객관성을 높인다. 사람마다 일이 다르니 방식을 그대로 가져가기보다 방법론을 각자 일에 녹이라. 「하나만 절대 믿으면 안 된다, 계속 검증해야 한다.」 |
| 2 | 「정직한 출구」는 실제로 어떻게 만들었나? | 결과가 아직 처리 중이면 간격을 늘려 가며 몇 번 재확인하게 하고, 그래도 안 되면 실행 기록을 붙여 「실패했다」고 보고하는 것도 성공으로 인정했다. |
| 3 | (의견) 규칙으로 정확히 처리할 일과 AI의 유연함이 필요한 일을 잘 나눠야 한다 | 동의. AI에게 참고 자료를 줄 때는 받아들이는 과정에서 손실이 생긴다는 걸 인정해야 하고, 거대한 자료는 작은 AI들에게 나눠 읽혀 요약을 남기는 편이 덜 까먹는다. |
| 4 | 출구를 둔다는 건 스킬을 덜 제약적으로 쓰라는 뜻인가? (요즘 스킬을 덜어내라는 말이 많은데) | 예측 가능한 실패(라이브러리 의존성 · 인증 401/403 등)가 있을 때 워크어라운드를 스킬과 훅으로 주는 것. 스킬을 가볍게 하라는 건 모델이 이미 할 줄 아는 것(베이스라인 61.8점에 들어 있는 것, 예: import는 맨 윗줄)을 빼라는 뜻이지, 스킬 없이 다 된다는 뜻은 아니다. |
| 5 | AI가 거짓말 못 하게 하려는 노력이 오히려 일을 늘리는 것 아닌가? 실제 생산성은? | 「10배, 100배 엔지니어가 됐다는 생각은 한 번도 안 했다.」 예전엔 20~25시간에 95점짜리, 지금은 3시간에 80점짜리. 80→90→100점은 훨씬 많은 시간과 집중이 든다. 「AI 세션을 몇십 개 띄워 놓고 일하다 보니 가장 중요한 자원은 토큰도 시간도 아니라 내 주의력.」 검증 장치를 촘촘히 만든 것도 사람이 덜 지치며 결과를 믿기 위해서. |
| 6 | 모델이 똑똑해질수록 착해지나, 더 음흉해지나? | 「착한 모델은 본 적이 없다. 다 어떻게든 저를 속여 먹으려고 덤비는 애들이라 어느 하나도 믿지 않는다.」 좋아질수록 더 교묘해지고, 사람이 지쳐 대충 넘기도록 결과물을 쏟아 내는 것도 꼼수. 「언젠가 사람이 못 찾게 되느냐」는 물음에 「이미 못 찾지 않나요?」 |
| 7 | 출구를 열어 주면 AI가 출구로 쉽게 빠져나가지 않나? | 아직 검증 못 한 가설: AI는 일을 받으면 먼저 계획을 세워 크기를 가늠하고, 한 번에 기억할 수 있는 양을 넘을 것 같을 때 꼼수를 택하는 것 같다. |
| 8 | 정말 정확해야 하는 서비스에서는 장치를 쌓기보다 사람이 일을 잘 쪼개 맡기는 게 더 중요하지 않나? | 지금 병목은 두 가지 — AI 결과물이 한 번에 회사 이름을 걸 품질에 이르지 못한다는 것, 사람의 리뷰가 AI가 쏟아 내는 양을 못 따라간다는 것. 그래서 오래된 실습 자료의 모델 이름 · 제품명을 최신으로 바꾸는 것처럼 「쉽게 검증할 수 있는 일부터」 맡기고 있다. |

## AI에게 속지 않는 7가지 습관 (일반 사용자용)

발표 내용을 바탕으로 Catch Up AI가 정리했다(발표자가 직접 제시한 목록은 아니다). 영상 마지막 화면과 칼럼에 같은 내용이 들어 있다.

1. **「다 했어요」는 확인하고 믿기** — 숫자 · 출처 · 결과를 한 번은 직접 확인한다.
2. **「모르면 모른다고 해도 돼」라고 먼저 말하기** — 지어낸 답이 줄어든다.
3. **듣기 좋은 답일수록 근거와 반대 의견 묻기** — AI는 맞장구 성향이 있다.
4. **다그치지 말고, 확인할 수 있게 해 달라기** — 「근거를 같이 보여 줘」.
5. **긴 자료는 나눠서 주기** — 부분마다 요약을 받아 본다.
6. **AI의 셀프 검토는 절반 — 한 번 더 확인하기** — 새 대화창이나 다른 AI, 다른 사람에게.
7. **최신 · 비싼 모델도 예외 없음** — 확인 습관은 모델을 바꿔도 계속 가져간다.
