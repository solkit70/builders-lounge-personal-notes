## 발표 내용

### Q. HebronGuide가 뭔가요?

**해외에 막 도착한 이민자의 정착을 돕는 커뮤니티 플랫폼**입니다. 성경 공부 앱이 아닙니다.

- 현재 **86개 도시, 16개국**에 진출
- 언어 3종 — 한국어 · 영어 · 스페인어
- 기관 파트너로 **World Relief** 연결
- **등록과 이용은 모두 무료**
- 웹사이트: https://www.hebronguide.com

**성격은 마켓플레이스입니다.** 위키형 정보 제공이 아니라 *환대를 제공하는 사람*과 *환대를 원하는 사람*을 잇는 매칭 플랫폼입니다. 발표자는 수요는 충분하고 **공급이 부족한 상태**로 진단했습니다.

### Q. HebronGuide는 왜 만들어졌나요?

**기본 정신은 '환대'입니다.**

김성수 목사님이 낯선 땅에 도착했을 때 아는 사람이 하나도 없고 안내해 줄 사람도 없는 막막함을 겪었습니다. 그때 어떤 분이 아무 대가 없이 아파트 열쇠를 건네줬고, 그 경험을 지금도 잊지 못한다고 하셨습니다.

> "그만큼 환대의 힘이라고 하는 게 굉장히 파워가 있다는 거예요. 사람은 교리보다 자신을 따뜻하게 맞이해주는 그 손길에 더 마음이 열리는 거예요."

개발자가 제품을 만들 때 사람들의 중요한 필요를 채우는 데서 시작한다면, 사람에게 가장 필요한 것이 무엇이냐 — 목사님의 답이 환대였습니다.

### Q. 김성수 님은 개발자인가요?

**아닙니다.** 코딩을 몰랐던 목회자이고, 바이브 코딩으로 직접 만드셨습니다.

> "코드라고 하는 걸 잘 몰랐던 사람이 어떻게 하나의 세계관을 붙들고 살다가 실제로 그 세계관을 현실 속에 실현할 수 있는 방법을 생각하다가 헤브론 가이드라고 하는 걸 만들었기 때문에…"

`HebronGuide 플랫폼 LLC`를 워싱턴주에 신고해 사업체로도 등록하셨습니다.

### Q. Conductor AI는 무엇이고 어떻게 동작하나요?

**서버를 24시간 감시하다가 장애가 나면 스스로 원인을 찾고 복구를 제안하는 시스템**입니다. 손민수 님이 만들고 계십니다.

**출발점** — 새벽 3시에 시스템이 멈춰 관련자를 전부 깨우고 다 같이 대응했는데, 나중에 분석해 보니 원인은 로그인 관련 서버의 아주 간단히 처리할 수 있는 이슈였습니다. *"이 정도 문제라면 AI가 스스로 분석하고 해결할 수 있지 않을까"* 에서 시작됐습니다.

**에이전트 7개가 역할을 나눠 갖습니다.**

| 에이전트 | 역할 |
| --- | --- |
| Judge | 메트릭 분석 · 의사결정 |
| Specialist | SSH로 심층 조사 (ReAct 패턴) |
| Flow | E2E 헬스체크 |
| Remedy | 복구 명령 생성 · 실행 |
| Airman | 음성으로 시스템 제어 |
| GitHub | 배포 · 커밋 히스토리 분석 |
| NewRelic | APM 메트릭 수집 |

**설계에서 눈여겨볼 지점**

1. **ReAct 패턴** — Specialist는 정해진 순서가 아니라 스스로 다음에 무엇을 볼지 고르며 조사합니다
2. **비용 설계** — 상태를 Normal / Warning(>70%) / Critical(>90%)로 분류하고 **Normal이면 LLM을 호출하지 않습니다.** 예상 월 비용 $50~100
3. **사람 승인** — 기술적으로 자동 복구가 가능한데도 실행 전 승인 단계를 넣었습니다
4. **RAG** — 과거 유사 사례를 찾아 컨피던스를 계산해 정답률을 높입니다

**기술 스택** — Go 1.21+ · Next.js 14 · Gorilla WebSocket · client-go(Kubernetes) · PostgreSQL + Qdrant · OpenAI GPT-4o · AWS EKS · New Relic · GitHub API

### Q. Conductor AI는 회사에서 쓰고 있나요?

**아직 아닙니다.** 취미로 만든 사이드 프로젝트가 아니라, **업무 중 겪은 문제를 풀기 위해 직원으로서 자발적으로 개발 중인 MVP**입니다. 실제 도입 여부는 회사가 판단할 몫입니다.

발표 중 *"쓰이고 안 쓰이는 거는 회사가 결정하는 일"* 이라고 직접 밝히셨습니다. 복구 실행 전 사람 승인 단계를 넣은 것도 *"회사에 쓴다고 하면 절대 AI가 자동으로 고치게는 안 할 걸 제가 알기 때문에"* 라는 판단에서입니다.

### Q. 왜 파이썬에서 Go로 바꿨나요?

**에이전트를 여러 개 동시에 돌릴 때 파이썬의 싱글 스레드 제한에 걸렸기 때문**입니다.

> "에이전트 수가 100개, 아니 30개만 넘어가도 파이썬의 싱글 스레드 제한이 있거든요. 아무리 비동기를 해도 하나씩 처리하는 파이썬의 고질적인 단점입니다."

Go로 옮긴 뒤에는 인텔코어 노트북 한 대에서 수십 개 네임스페이스의 파드를 감시하며 수십 개 에이전트를 동시에 돌리고 있습니다. goroutine이 이 용도에 따라갈 게 없다는 이야기였습니다.

### Q. Quant 에이전트는 무엇인가요?

**이도규 님이 회사에 다니면서 만든 개인용 퀀트 투자 에이전트**입니다.

메일과 뉴스레터로 들어오는 종목 정보를 모아 일간 다이제스트로 만들고, 에이전트가 그것을 분석해 매수·매도 신호를 냅니다. 결과에 본인 포트폴리오를 붙여 대조하는 방식이고, 계좌 성격(은퇴 계좌 ETF, 직접 운용 계좌 등)에 따라 관점을 나눠 봅니다.

데이터는 FRED·Yahoo 등 **무료 API**를 쓰고 있으며, 발표자 본인이 *"유료 API를 쓰는 게 제일 확실하다"* 고 한계를 인정했습니다.

**영상에서 가장 인상적인 장면** — 본인이 정한 *"실적 발표 전에는 사지 말자"* 는 규칙을 스스로 어겼더니, 에이전트가 **왜 규칙을 어겼냐고 되받아칩니다.**

### Q. Bila AI는 무엇인가요?

**창발 Space에 올라간 글과 GitHub 저장소의 기록을 참조해 모임 관련 질문에 답하는 에이전트**입니다. 강민석 님과 박창수 님이 만들고 있습니다.

4차 모임에서는 **개회 진행을 Bila AI에게 맡겼습니다.** 시작 직후 할루시네이션이 발생했고 즉석에서 지적받았는데, 이를 숨기지 않고 그대로 노출했습니다. 완성 후 공개가 아니라 미완성 상태로 사용자 앞에 세우는 방식입니다.

4차 모임에서 **모바일 앱 출시 소식**까지 나왔습니다.

### Q. "무엇이 에이전트인가" 논쟁은 어떤 내용이었나요?

마지막 자유 발표에서 정의 논쟁이 붙었습니다. 결론은 두 가지 기준으로 정리됐습니다.

**① 룰 베이스인가, AI 판단인가**
조건이 미리 정해져 있어서 "이런 경우엔 이게 Root Cause"라고 규정돼 있으면 **에이전틱이 아닙니다.** 로그를 보고 AI가 판단해 Root Cause를 내고, 그 근거로 해결책까지 제시하면 에이전틱한 접근입니다.

**② 실행 중 LLM을 호출하는가**
더 실용적인 기준입니다. 코드 에이전트로 만들었더라도 앱이 도는 동안 LLM을 한 번도 호출하지 않으면 그냥 자동화 프로그램입니다.

> 한국의 지인이 만든 투자 앱은 코드로 매매 로직을 짜고 LLM을 한 번도 호출하지 않는다 → 에이전트가 아니다
> 앱 안에서 LLM을 호출해 정보를 가져와 처리하고 그 결과를 다시 쓴다 → 에이전트로 볼 수 있다

### Q. 손민수 님 에이전트는 2차 모임과 무엇이 달라졌나요?

**2차 모임(6월)에서는 개발 1주차 MVP로 컨셉만 보여주셨습니다.** GateKeeper·Specialist·Judge 세 단계로 장애를 판단한다는 구조만 있었습니다.

**두 달 뒤 4차 모임에서는 라이브 데모로 돌아왔습니다.** 이름이 Conductor AI로 붙었고, 메모리를 90%까지 올리는 스트레스 테스트를 걸자 에이전트들이 서로 대화하며 Root Cause를 찾아 파이썬 프로세스의 PID까지 특정하고, 복구 방법 세 가지를 후보로 제시했습니다.

**Planning Agent도 추가됐습니다.** 서버마다 고유의 Goal을 두고 5분마다 *"현재 내 골을 만족하고 있나"* 를 점검하는 루프입니다. 발표자는 이를 게임 프로그래밍의 거대한 while 루프에 비유했습니다. 장애 대응(사후)에서 목표 유지(상시)로 성격이 확장된 셈입니다.

### Q. 김성수 님은 어떻게 4차 모임 발표자가 됐나요?

**3차 모임에서 만난 분입니다.** 2026년 7월 6일 KACC Coffee Chat(3차)에 HebronGuide 대표로 참석하셨고, 그 자리에서 나온 *환대(hospitality)* 논의가 한 달 뒤 4차 메인 발표로 이어졌습니다.

모임이 발표자를 외부에서 섭외하는 것이 아니라 **커뮤니티 안에서 만들어내고 있다**는 사례입니다.
