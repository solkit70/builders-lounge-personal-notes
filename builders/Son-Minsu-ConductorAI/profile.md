## 한 줄 소개

**샌프란시스코시 IT 공무원.** 업무 중 겪은 새벽 장애 대응 경험에서 출발해 **서버 장애를 스스로 진단·복구하는 에이전트 Conductor AI**를 만들고 있다. Builders Lounge **5차 모임 메인 스피커**.

## 제품 — Conductor AI

**서버를 24시간 감시하다가 장애가 나면 스스로 원인을 찾고 복구를 제안하는 시스템.**

> ⚠️ **사이드 프로젝트가 아니다.** 업무 중 겪은 문제를 풀기 위해 **직원으로서 자발적으로 개발 중인 MVP**이고, 실제 도입 여부는 아직 회사가 판단하지 않았다. 발표 중 *"쓰이고 안 쓰이는 거는 회사가 결정하는 일"* 이라고 직접 밝혔다.

### 출발점

새벽 3시에 시스템이 멈춰 관련자를 전부 깨우고 다 같이 대응하느라 한바탕 난리가 났는데, 나중에 분석해 보니 원인은 **로그인 관련 서버의 아주 간단히 처리할 수 있는 이슈**였다.

> "이 정도 문제라면 AI가 스스로 분석하고 해결할 수 있지 않을까?"

### 에이전트 7개 — 역할 분담

| 에이전트 | 역할 |
| --- | --- |
| **Judge** | 메트릭 분석 · 의사결정 |
| **Specialist** | SSH로 심층 조사 (**ReAct 패턴**) |
| **Flow** | E2E 헬스체크 |
| **Remedy** | 복구 명령 생성 · 실행 |
| **Airman** | 음성으로 시스템 제어 |
| **GitHub** | 배포 · 커밋 히스토리 분석 |
| **NewRelic** | APM 메트릭 수집 |

### 설계에서 눈여겨볼 지점

**1. ReAct가 실제로 도는 방식** — Specialist는 정해진 순서로 명령을 실행하지 않는다. `get_top_cpu_processes()` → `get_java_heap_info()` → `get_docker_logs("tomcat")` 순으로 **스스로 다음에 무엇을 볼지 고르면서** 결론에 도달한다.

**2. Normal일 때는 AI를 부르지 않는다** — 상태를 Normal / Warning(>70%) / Critical(>90%)로 분류하고 Normal이면 LLM을 호출하지 않는다. 사고는 자주 일어나지 않으므로 대부분의 시간에 비용이 0이다. **예상 월 비용 $50~100.**

**3. 고치기 전에 사람이 승인한다** — 기술적으로 자동 복구가 가능한데도 승인 단계를 넣었다. *"회사에 쓴다고 하면 절대 AI가 자동으로 고치게는 안 할 걸 제가 알기 때문에"* — 조직에 제안하기 위한 설계 판단이다.

**4. 파이썬에서 Go로 다시 썼다** — *"에이전트 수가 100개, 아니 30개만 넘어가도 파이썬의 싱글 스레드 제한이 있거든요."* Go로 옮긴 뒤 인텔코어 노트북 한 대에서 수십 개 네임스페이스의 파드를 감시하며 수십 개 에이전트를 동시에 돌린다.

**5. RAG로 과거 사례를 비교한다** — 데이터베이스에 자료를 쌓아 두고 유사 사례를 찾아, 그때의 해결책에 붙은 평가로 **컨피던스를 계산**해 정답률을 높인다.

**6. Planning Agent** — 서버마다 고유의 **Goal**을 두고 5분마다 *"현재 내 골을 만족하고 있나"* 를 점검하는 루프. 게임 프로그래밍의 거대한 while 루프에 비유했다. 장애 대응(사후)에서 목표 유지(상시)로 성격이 확장됐다.

### 기술 스택

Go 1.21+ · Next.js 14 · Gorilla WebSocket · client-go(Kubernetes) · PostgreSQL + Qdrant(RAG) · OpenAI GPT-4o · AWS EKS · New Relic · GitHub API
